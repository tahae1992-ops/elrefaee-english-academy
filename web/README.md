# Elrefaee English Academy — Web App

The platform's Next.js application. Architecture, product, and design decisions are governed by the planning documents in [`/docs`](../docs) (00–11) — this README covers only what's specific to running and working in this codebase.

## Getting started

1. **Node.js 24 LTS** and npm are required.
2. Copy the environment template and fill in real values (get them from the Supabase dashboard for the `elrefaee-academy-dev` project, ref `pgepcmtqxlsezyzzwjrm`):
   ```bash
   cp .env.example .env.local
   ```
3. Install dependencies and start the dev server:
   ```bash
   npm install
   npm run dev
   ```
   Open [http://localhost:3000](http://localhost:3000). The app runs fine with an unconfigured `.env.local` — `/api/v1/health` will correctly report `unhealthy` until `DATABASE_URL` is set, and Sentry stays a no-op until a DSN is provided.

## Architecture

Clean Architecture + DDD, per [SAD §6.1](../docs/04-system-architecture-document.md). Each bounded-context module lives under `src/modules/{context}/` with four layers:

```
src/modules/<context>/
  domain/           # entities, value objects — zero framework/IO dependencies
  application/      # use cases, orchestrating domain via ports (interfaces)
  infrastructure/   # port implementations (Drizzle repositories, adapters)
  interface/        # thin controllers called by Next.js Route Handlers
```

Only a module's `interface/` layer (or `src/composition-root.ts`, which wires Infrastructure into Application across every module) may be imported from outside that module. This is enforced in CI, not just documented — see `.dependency-cruiser.cjs` and `npm run arch:check`.

`src/shared/infrastructure/db/` holds the one Postgres connection every module's repositories share, and the 11 bounded-context schema declarations (`schemas.ts`, DDD §1).

## Database migrations

Migrations live in `drizzle/migrations/`, generated by `drizzle-kit` from `src/**/infrastructure/db` schema files (currently just the 11 schema declarations — tables land as each owning module is built). Every migration ships with a hand-authored `.down.sql` rollback alongside it (drizzle-kit has no built-in down-migration runner) — see `0000_init_schemas.down.sql` for the pattern. **Read the rollback file's own caveats before running one** — a rollback that was safe when authored (e.g., against empty schemas) may not stay safe once later migrations add data.

## Testing

Unit tests (`*.test.ts(x)`) never touch a live database — ports are faked, per Clean Architecture's whole point. Integration tests (`*.integration.test.ts`, run via `test:integration`) will exercise real infrastructure adapters against a real database once a later sprint adds one with actual tables to test against.

## Known, tracked dependency findings

`npm run audit:check` passes with a reviewed allowlist (`audit-ci.jsonc`) for 3 advisories nested inside Next.js's and drizzle-kit's own bundled dependencies (not something this project's `package.json` controls directly, and no upstream fix exists yet without a major framework downgrade). Each entry documents why it's accepted and what would make it worth revisiting — check there before assuming a new audit failure is one of these.

## CI

`.github/workflows/ci.yml` runs lint, typecheck, the architecture check, unit tests, and a production build on every PR and push to `main`, plus a separate dependency-audit job. Vercel preview deployments require one manual one-time step: importing this GitHub repo into a Vercel project via the [Vercel dashboard](https://vercel.com/new) (the available Vercel tooling in this environment can deploy files directly but can't perform the GitHub App repo-linking Vercel's native PR-preview integration requires) — see the Sprint 1 summary for details.
